# MPLS Playlists Encode Mechanism, Never Meaning

The Blu-ray MPLS format contains no field that classifies a playlist as a movie, episode, play-all, or language variant. The `AppInfoPlayList` block exposes only operational flags — sequential/random playback mode, user-operation restrictions, audio-mix permissions, and a single 3D stereo bit — with content-type classification left entirely to heuristic inference by consuming tools. libbluray, MakeMKV, and HandBrake each implement their own structural filtering pipeline based on PlayItem clip identity, total duration, and chapter counts; none exposes a guaranteed "episode" signal. For code that needs to detect episodes on a BD disc, the most reliable structural proxy is the segment map (PlayItem clip list), used in combination with duration thresholds and chapter counts, and anchored to the authoritative title table in `MovieObject.bdmv`. Java-driven play-all playlists and single-segment all-episodes discs remain opaque to static MPLS inspection.

## The MPLS binary format carries operational flags only

An MPLS file begins with a 4-byte ASCII magic value `MPLS`, a 4-byte version string (typically `0200`), and three 32-bit big-endian offsets to the PlayList, PlayListMark, and optional ExtensionData sections — all integers are big-endian throughout ([Wikibooks User:Bdinfo/mpls](https://en.wikibooks.org/wiki/User:Bdinfo/mpls)). The `AppInfoPlayList` block, at offset `0x28`, is almost always 14 bytes long and contains three fields that matter to detection code: a **`playback_type` byte** (`1` = sequential, `2` = random, `3` = shuffle), a 2-byte `playback_count` used only in random/shuffle mode, and a `miscellaneous_flags` byte whose bits cover `random_access_flag`, `audio_mix_flag`, `lossless_bypass_flag`, and, since a LAV libbluray patch, `mvc_base_view_r_flag` (the MVC stereo base-view orientation for 3D discs) ([LAV libbluray commit](https://gitea.1f0.de/LAV/libbluray/commit/768d9c6add9b7e42651e31be055539c4ecdd8ba2)). There is no `content_type`, `playlist_type`, or `application_type` field at the playlist level; the spec is not publicly available and this gap in the reverse-engineered documentation is confirmed by every open-source parser ([docs.rs mpls crate](https://docs.rs/mpls/latest/mpls)).

Content-type information does exist at the clip level, not the playlist level. Each CLPI (ClipInfo) file carries a `clip_stream_type` byte and an **`application_type` byte** in its `ClipInfo` block; `application_type` values 1–7 distinguish main-path transport streams from sub-path streams such as menus, slide shows, and text subtitles, with value 1 identifying a movie's main-path clip and value 6 identifying a sub-path text-subtitle clip ([libbluray clpi_data.h](https://git.stg.centos.org/source-git/libbluray/blob/4331df799a6453407bd4175499c11617e982cee7/f/src/libbluray/bdnav/clpi_data.h)). Critically, `application_type = 1` applies equally to a movie, a TV episode, and a bonus featurette — the distinction between those three categories does not exist anywhere in the standard binary structures. All classification is post-hoc inference.

The `PlayListMark` section adds chapter information: each 14-byte entry holds a `mark_type` (`1` = Entry Mark / chapter, `2` = Link Point), a PlayItem ID, a timestamp in **45000ths of a second**, an elementary-stream PID (usually `0xFFFF`), and a duration (`0` = no fixed duration) ([Wikibooks User:Bdinfo/mpls](https://en.wikibooks.org/wiki/User:Bdinfo/mpls)). Chapter count and chapter timestamps are therefore readable directly from MPLS without touching the M2TS clips.

## Structural signals that proxy for content type

Because no spec enum exists, every tool in the ecosystem falls back to four structural proxies: **segment map** (the ordered list of M2TS clip filenames referenced by a playlist's PlayItems), **total duration**, **PlayItem count**, and **chapter count**.

The segment map is the most discriminating signal. A single-episode playlist references exactly one or two clips; a play-all playlist for a five-episode disc lists all five episode clips in order — a segment map of `"1,2,3,4,5"` versus `"2"` identifies the two playlist types unambiguously when the disc is well-authored ([MakeMKV forum, segment map explanation](https://forum.makemkv.com/forum/viewtopic.php?p=53072)). Because episode M2TS clips are not always numbered by episode order (Westworld Season 1 disc: playlist 105 precedes 107 precedes 103), the play-all playlist is also the only reliable way to determine episode sequence from the disc structure alone ([MKVToolNix forum](https://help.mkvtoolnix.download/t/segment-map-for-tv-series/1513)). When the play-all playlist is identified, the order of its PlayItems directly encodes the correct episode sequence.

Language variants add a wrinkle. Disney discs use the `00800`-series MPLS range for per-language variants: `00800.mpls` is English, `00801.mpls` Spanish, `00802.mpls` French, each sharing most clips but substituting a small set of localized clip IDs for opening titles and credits ([MakeMKV forum, Rogue One thread](https://forum.makemkv.com/forum/viewtopic.php?p=55134)). This is a studio convention — the `00800`+ range carries no special meaning in the spec — and its extent varies by studio. The authoritative source for playlist-to-title mapping is `MovieObject.bdmv`, which contains the actual playback commands (`"play playlist XYZ"`), with `index.bdmv` mapping disc title numbers to movie objects ([MKVToolNix forum, mbunkus reply](https://help.mkvtoolnix.download/t/segment-map-for-tv-series/1513)). For a correct determination of the "real" playlist in any given disc, parsing `MovieObject.bdmv` is both more reliable and more principled than guessing by MPLS number range.

## libbluray's filtering pipeline: what TITLES_RELEVANT actually does

libbluray's public API exposes three filter flags for `bd_get_titles()`: **`TITLES_ALL = 0`**, **`TITLES_FILTER_DUP_TITLE = 0x01`**, and **`TITLES_FILTER_DUP_CLIP = 0x02`**; `TITLES_RELEVANT = 0x03` is their bitwise OR ([libbluray bluray.h](https://videolan.videolan.me/libbluray/bluray_8h_source.html)). The third argument, `min_title_length`, provides a duration floor in seconds. The logic runs in `navigation.c`, not in the MPLS parser.

`_filter_dup()` does a structural comparison: it compares `list_count` (PlayItem count) and, for each PlayItem, the clip filename plus `in_time` and `out_time`. If all fields match, the second playlist is dropped as a duplicate ([libbluray-devel mailing list, 2014](https://mailman.videolan.org/pipermail/libbluray-devel/2014-May/001457.html)). A 2014 HandBrake-proposed patch extended this comparison to also check per-stream attributes (stream type, coding type, PID, language code, and stream counts per play item); this stricter comparison would treat alternate-language variants as duplicates, whereas the baseline comparison preserves them because different audio PIDs make the per-clip structures differ. Whether this patch was merged into upstream libbluray or lives only in downstream forks (Nixpkgs, LAV) is unconfirmed.

`_filter_repeats()` / `_find_repeats()` target a different pattern: **a single playlist that references the same clip with identical in/out times across multiple PlayItems** — a structure typical of menu loops or anti-ripping decoys rather than genuine content. The exact repeat threshold was not recovered from available sources. A 2019 libbluray commit added HEVC codec preference as a tiebreaker in main-title selection ([libbluray commit history](https://code.videolan.org/videolan/libbluray)).

The consequence for play-all detection is counterintuitive: `TITLES_FILTER_DUP_CLIP` may *remove* the play-all playlist or the individual episode playlists depending on filesystem processing order, because both sets reference the same underlying M2TS clips. libbluray has no API to say "this is a play-all"; the effect is structural elimination rather than semantic classification. FFmpeg's `bluray.c` calls `bd_get_titles(bd, TITLES_RELEVANT, 180)` and then picks the **longest duration** title ([FFmpeg bluray.c, camenduru mirror](https://huggingface.co/camenduru/ffmpeg-cuda/blob/main/libavformat/bluray.c)) — a heuristic that works for movies but silently fails on TV series discs where multiple episodes have equal durations.

## MakeMKV and HandBrake: distinct strategies on the same foundation

MakeMKV is closed source in its binary analysis layer. Its visible behavior shows a segment-map identity check similar to libbluray's `_filter_dup`: when two playlists reference the same ordered sequence of M2TS clips, MakeMKV logs `"title 6 is the same as title 7, and was therefore skipped"` ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=52406)). For discs with **Java playlist obfuscation**, MakeMKV uses a bundled Java Runtime to execute the disc's BD-J code and tag the identified main feature with **`(FPL_MainFeature)`** in its title list ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=95219)); version 1.16.4 (2021) brought "much better support for discs with Java playlist obfuscation" ([VideoHelp MakeMKV version history](https://videohelp.com/software/MakeMKV/version-history)). Without Java, MakeMKV presents all playlists that pass its structural filter and relies on the user to match durations and segment maps to episode identities.

HandBrake uses libbluray directly via `libhb/bd.c`. It **always** passes `TITLES_FILTER_DUP_CLIP` and adds `TITLES_FILTER_DUP_TITLE` unless the user sets `--keep-duplicate-titles` (added in HandBrake 1.9.0, [PR #5985](https://github.com/HandBrake/HandBrake/pull/5985)). It passes `min_title_length = 0`, meaning even sub-second playlists pass the duration floor. After scanning, it **sorts titles by MPLS number** (`title_info_compare_mpls` comparator), so title index 0 always corresponds to the lowest-numbered `.mpls` file, not the longest. `hb_bd_main_feature()` selects a main-feature candidate using the **70% duration rule**: any title whose duration is ≥ 70% of the longest title is a candidate; within candidates, ties break on video format rank (preferring HEVC/higher-quality codecs), then duration, then chapter count ([HandBrake libhb/bd.c](https://github.com/HandBrake/HandBrake/blob/master/libhb/bd.c)). HandBrake performs no episode-specific detection; the main-feature heuristic will naturally select a play-all playlist as the default encode target on a TV series disc, since it is usually the longest title.

## Known edge cases that break every heuristic

Five structural patterns defeat straightforward segment-map or duration approaches in documented real-world discs.

**Fake/decoy playlists** are the most common anti-ripping technique. Titles like *John Wick* contain 300+ near-identical MPLS files pointing to the same M2TS clips in different permutations ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=173579)); libbluray's `_filter_dup` removes clip-identical permutations but cannot remove permutations that differ by even one in/out time boundary. MakeMKV's Java FPL detection is required to navigate these discs correctly.

**Single-segment all-episodes discs** encode all episodes into one long M2TS clip, relying on chapter markers for episode boundaries. *Adventure Time* Australian Season 7 exhibits this pattern; *Rick and Morty* Season 1 title 11 was documented as "a combination of all episodes in 1 large file" ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=56602)). A segment-count heuristic reports `1` for both a single-episode playlist and this type of play-all; only duration (much longer than a single episode) combined with a high chapter count distinguishes them.

**BD-J Java play-all playlists** have no corresponding MPLS structure at all. The "Play All" functionality is implemented in Java code that sequences individual episode playlists at runtime; tools that cannot execute BD-J (most Linux-based tools) have no way to detect or represent this pattern from static file inspection alone ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=53072)).

**Duration-identical multi-variant episodes** defeat duration-based filtering. *Band of Brothers* Blu-ray disc 3 has four titles at exactly 1:07:20 and four more at exactly 55:42; the four variants of each episode are distinguished by "hidden tracks" (alternate audio or angle tracks) rather than duration ([VideoHelp forum](https://forum.videohelp.com/threads/350950-Which-Title)). A duration-only heuristic cannot choose among them.

**False-positive duplicate filtering** causes missed episodes. A *Transformers Prime* Season 1 Disc 3 user confirmed one episode was skipped by MakeMKV's duplicate filter ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=63515)); *South Park* Season 15 Disc 2 consistently fails to surface episode 4 across multiple MakeMKV versions ([MakeMKV forum](https://forum.makemkv.com/forum/viewtopic.php?p=63510)). These failures demonstrate that `TITLES_FILTER_DUP_CLIP` can collapse genuinely distinct episode playlists when their clip structures happen to overlap.

## Conclusion

The practical design for robust BD episode detection code follows from this evidence. **Layer three signals in order of reliability:** first, compare PlayItem clip lists (segment maps) to identify multi-clip playlists as play-all candidates and single-clip playlists as episode candidates; second, apply a duration floor calibrated to expected episode length (the community-validated default from `bluback` is 900 seconds, appropriate for drama; anime needs ~1200 seconds); third, use chapter count as a tiebreaker to distinguish single-segment play-all playlists from genuine single-episode playlists with few chapters. For episode ordering, extract the PlayItem sequence from the play-all playlist rather than trusting MPLS file numbers, which are unordered by spec and author convention.

Two categories of disc will always require either BD-J execution or manual intervention: Java-driven play-all playlists and deeply obfuscated fake-playlist discs. For automated pipelines, logging the full title list with segment maps and flagging any disc where the filtered title count diverges sharply from the expected episode count is the most practical safeguard — signaling that the disc needs special handling without silently producing wrong output.
